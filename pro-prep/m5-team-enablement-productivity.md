## Screen 1 (S01) — モジュール・オリエンテーション

### モジュール・オリエンテーション
オリエンテーション：このモジュールでできるようになること

最初の4モジュールで、あなたは「ステークホルダーの最初の一言から設計・統合・ガバナンス・引き渡しまでを行えるアーキテクト」になりました。このモジュールは、そのデプロイメントを支えるチームについてです。チーム全体がClaudeで生産的に仕事をできるようにし、システムが本番稼働した後も生産性を維持する方法を学びます。

このモジュールを終えると、以下ができるようになります：
1. チーム向けのClaudeツーリングと環境を構成する（共有設定、展開パターン、スキル配布戦略、チームセットアップに含めるべきSpend posture（コスト管理態勢））
2. AIツールで開発ワークフローを改善し、AI生成物が本番に届く前に信頼性を担保するレビュー規律を定義する
3. デバッグと運用上の問題解決をサポートする（症状をアーキテクチャ原因に結びつけ、チームの自律性を高める）

### このモジュールのテーマは「エイブルメント」

これまでのモジュールは「Claudeを構築・設定する方法」を教えてきました。このモジュールは「システムは構築済み」と仮定し、以下を問います：チームはそれをどのようにうまく採用するか？ すべての問題にアーキテクトが介入しなくても、システムを健康に保つには？ チームセットアップは、誰もログインする前に、環境・再利用可能アセット・Spend posture（コスト管理態勢）を適切に整えます。開発ワークフローは、品質バーを下げずにチームの日々の作業を向上させます。運用サポートは、チームがシステム内で予期しない事象に遭遇した際に行う対応です。

これら3つのトピックは相互に積み上がります。セットアップ段階で配布するスキルは、開発ワークフローでも活用されるアセットそのものです。ワークフローのために確立したレビュー規律は、運用上の問題発生時にプレッシャー下で試されるものです。3つはこの順序で進めます：環境をセットアップし、日々のワークフローを向上させ、システムを健康に保つ。

## Screen 2 (S02) — チームセットアップ

### チームセットアップ
チーム向けのClaudeツーリングと環境の構成

自分一人であればClaudeの設定は数分で済みます。しかし、チーム向けの設定は違います。チーム設定には、全員が同じベースラインから始めるための共有デフォルト、一元管理で更新・取り消し可能な再利用可能アセット、数十人の利用規模が拡大しても範囲内に留まるコスト管理が必要です。この画面では、アーキテクトが責任を持つ4つのチームセットアップ判断項目（環境・展開・スキル配布・コスト）と、それぞれをスキップした場合に発生する失敗について扱います。

### 環境を共有設定としてデプロイする

チーム環境は共有設定です：個々人の個別設定ではなく、すべての開発者がそこからスタートするベースラインです。Claude Codeで言えば、チームはプロジェクトレベルのベースラインで合意することを意味します：共有のCLAUDE.md、合意されたツールとMCPサーバーのセット、権限設定。これにより、誰もが同じ場所からスタートし、それぞれが場当たり的な設定を見つけてバラバラに逸脱していくのを防ぎます。そのベースラインは、レビュー・バージョン管理・改善を全員向けに一度に行えるものです。

### チャンピオンから、バッチ単位で展開する

チーム全体での採用が「全員一斉有効化」で成功することは稀です。最も効果的なパターンは、各部署やチームごとにチャンピオンを1人特定し、その人に最初にアクセスを付与して実際のワークフローで実証してもらい、その後バッチ単位で採用を広げていく方式です。チャンピオンが初期の摩擦を吸収し、ローカルな例を構築し、第一線のサポートとなることで、アーキテクトだけがチームの質問に答える状況を回避します。

#### 実例
200人のエンジニアリング組織が4部署にClaude Codeを導入したいとします。4部署全てを一度に有効にするのではなく、アーキテクトは各部署のチャンピオン1人にアクセスを付与し、2週間かけて実際のワークフロー（コードレビューアシスト、テスト生成ステップなど）を転換してもらいます。その後、各チャンピオンが同僚5人を含む最初のバッチ向けに45分セッションを実施します。広範な展開が始まる頃には、すべての部署に実働例・ローカルの専門家・チャンピオンが既に調整済みの共有CLAUDE.mdが存在しています。これを一斉メールで実行した場合、混乱する初心者のプロンプトが急増し、古い習慣へと静かに退行してしまったでしょう。

### スキル配布：再利用のチームスケール版

スキルパッケージは「バージョニング可能で再利用可能な単位として現れる反復可能手順」であることを学びました。チームスケールでのアーキテクチャ上の問いはこうです：スキルをチーム全体にどのように配布すべきか？ 作成・バージョニング・公開方法、アクセス権の付与・取消方法、スキルが不具合を起こした場合のロールバック方法を考慮する必要があります。チームスキル配布には主に4つの方法があり、選択するメカニズムはツールの種類、使用者、管理権限者によって異なります。

スキルをチームにデプロイする方法は4つあり、アクセス可能な人物と保持する管理レベルが異なります。Organization settings > Skillsでアップロードされた「Org-provisioned Skill（組織プロビジョニング）」は、組織内全員にいちどきに利用可能になります。能力が真に全メンバーに届くべき場合の最もシンプルな経路です。特定のメンバーのみに届けるべき場合、1つ以上のスキルをプラグインにまとめ、グループに割り当てます。そのグループのメンバーのみがそれらのスキルにアクセスできます。プラグインは管理された配布の場でもあります：必須・デフォルトインストール・利用可能・利用不可といったインストール設定、グループターゲティング、接続リポジトリからのバージョン管理された更新などです。第3のメカニズムはClaude Codeプロジェクトスキル：ファイルシステムアーティファクトとしてプロジェクトリポジトリ（.claude/skills/）に存在し、リポジトリ自体でバージョニングされ、それを持つプロジェクトにスコープされます。第4はAPIスキル：パートナー自社製品からプログラム的に呼び出されます。一元管理されたClaude Code設定は全く別チャネルです：サーバー管理設定はAnthropicのサーバーからユーザー認証時・1時間ごとのポーリングサイクルで配信されます — 設定メカニズムであり、スキル配布パスではありません。

### スキル配布メカニズム

| 配布メカニズム | 最適な場面 | 管理・ロールバック |
|---|---|---|
| **Org-provisioned Skill**（Organization settings › Skills） | 能力が組織内全員に届くべき場合 | 組織全体での組織管理による可用性と削除。ユーザーは個別スキルをOFFにできるが削除は不可。バージョンピン留やネイティブロールバックなし；更新には手動再アップロードが必要 |
| **Plugin assigned to a group / org** | 特定チームに届けるべき手順・ツール群、または管理された展開が必要な場合 | グループターゲティング、プラグインが必須・デフォルトインストール・ユーザー利用可能（現在の管理者UIの正確ラベル、サポート記事13837433）を制御するインストール設定、接続リポジトリからのバージョン管理された更新。グループスコープ配布の最も強力な管理オプション。これは、以前のバージョンに戻るパスを持つ唯一のメカニズムではない：APIスキルは明示的なバージョンピン留をサポートし、Claude Codeプロジェクトスキルはそれを持つリポジトリと共にロールバックする |
| **Claude Code project Skill** | 1チームが自プロジェクト間で共有するツール・規約 | プロジェクトリポジトリ（.claude/skills/）内のファイルシステムアーティファクト、リポジトリと共にバージョニングされ、それを持つプロジェクトにスコープされる |
| **API Skill**（Messages API container） | パートナー自社製品がプログラム的に呼び出す能力 | 呼び出しシステム内で管理；明示的なバージョンピン留をサポート；再利用はマシン間（人間向けではなく） |

チームワークフローを配布可能スキルとしてパッケージングすることで、良質なローカルプラクティスがチーム標準になります。手順は文書化されないノウハウではなく、管理された1アーティファクトとして移動し、更新は再説明ではなくバージョニングを通じて伝播します。

### 最初の請求書の前にSpend posture（コスト管理態勢）をセットする

チームセットアップにはコストガードレールも含まれます。管理者はデフォルトを継承せず、意図的に設定すべきです：モデルデフォルト（セッションの開始モデル）、モデル許可リスト・制限（チームが切り替え可能なモデル）、エフォートガイダンス（モデルがタスクにどれほど努力するか）、コスト・レート・ユーザー別上限で消費を範囲内に留めます。Module 2で見たように、モデル選択を未管理にしておくと、作業がタスクに必要なより有能力で高価なティアに静かにルートされる可能性があります。チームスケールでは、その選択がすべてのメンバー・すべてのリクエストで掛け算されます。

#### **要注意：**
戻る道のないスキル配布

プラットフォームチームがリリースノート手順をスキルとしてパッケージ化し、プラグインにまとめて40人のエンジニアグループに割り当てました。1週間後、善意の編集がプロンプトを変更し、スキルが使用するすべてのチームで誤ったフォーマットでノートを出力し始めました。スキルはバージョン管理された更新・ロールバックを提供するプラグイン形式ではなくフラットバンドルとしてプッシュされていたため、修正には手動再編集が必要で、不正な出力が出続けました。スキル自体は良いアイデアでしたが、必要な管理なしに配布されました。バージョンも戻る道もない共有アセットは、複数人が依存した瞬間から負債になります。共有アセットにバージョニング・グループターゲティング・ロールバックが必要な場合、組織管理プラグイン内に配布し、所有者を特定してください。

#### **コスト・複雑さ・リスク**

| **コスト** | チーム環境の構築にはセットアップ時間がかかります：共有設定、展開計画、スキルのパッケージ化ですが、後で40個の逸脱した設定を調整するよりは遥かに安上がりです |
| **複雑さ** | 難しいのは配布管理：誰が各共有アセットに到達・更新・取り消しできるか。アセットごとに決定してください |
| **リスク** | 最大の失敗モードは、バージョニング・ロールバックなしの共有アセット（スキル・設定等）で、1つの悪い変更が誰も止められないうちにチーム全体に伝播すること |

## Screen 4 (S04) — 開発ワークフロー

### 開発ワークフロー
AIツールによる開発ワークフローの改善

Claudeを完璧に設定してもチームがほとんど得られないことがあります。違いはワークフローです：AIアシスタンスが開発者の作業方法に織り込まれているか、そしてその出力を信頼できるようにする規律があるかです。この画面では、品質バーを下げずにワークフローバーを上げる方法と、後半をスキップした場合に発生する失敗について扱います。

### 既存ワークフローにアシスタンスを統合する

AIツールは既存ワークフローの中に生きるときに効果を発揮します：エディタ、レビュープロセス、テストループの中であって、開発者がたまに訪れる別のチャットウィンドウではありません。アーキテクトの仕事は、AIアシスタンスがどこの実際の摩擦を取り除き、全体プロセスを改善できるかを見つけることです。Claudeはチームの現在のワークフローに統合されるべきです。統合こそが、チームの知識と作業方法がエンコードされる方法でもあります。規約、レビュー基準、反復される手順が通常は人々の頭の中に住んでいますが、それらがスキルとプロジェクト設定になり、Claudeが一貫して適用するため、良いプラクティスはツーリングと共に移動し、その部屋に誰がいるかに依存しなくなります。

### 各ワークフロー段階でClaudeが助けられることと、依然として必要なレビュー規律

| ワークフロー段階 | Claudeが助けられること | 依然として必要なレビュー規律 |
|---|---|---|
| **コードを書く** | 明確な仕様からボイラープレート・テスト・第一実装をドラフト作成 | 正確性・セキュリティレビュー；生成された内容を作者が理解している必要 |
| **コードをレビューする** | diffの要約、問題の可能性フラグ、馴染みないコードの説明 | 呼び出しの人間的判断；AIフラグは入力であり、判定ではない |
| **デバッグする** | 症状とトレースから仮説を提示 | 行動前に証拠に対して仮説を検証 |

### 2つの失敗モードが繰り返し現れる

1. **不均一な採用**：一部の開発者がAIツーリングを重用し、残りがほとんど使わない状態。チームがツールの実際の利得を得られず、プラクティスが標準化されません。前のトピックのチャンピオン・バッチ展開はこれを回避する良い方法です：早期採用者に任せるのではなく、意図的に使用を広げます。
2. **ベーシックチャットでの停滞**：チームがClaudeを質問応答ボックスとして使い、tool use、リポジトリ対応アシスタンス、パッケージスキルなどの高価値ワークフローに進めません。誰も最初の一歩を超えて有効化しないからです。チームにアクセスを提供しても採用ではありません；現在のワークフロー内での本格的なエイブルメントを構成する必要があります。

### 勤勉さ：AI生成作業を信頼できるものに保つ規律

勤勉さ（Diligence）は4つのAI Fluency能力の1つです。Anthropicはこれを「AIで何をするか、どう行うかに対する責任を取ること」と定義しています。デプロイメント勤勉さは具体的には、使用・共有する出力を検証し保証する責任を取ることを意味します。開発ワークフローに適用すると、その責任は具体的な習慣として現れます：AI生成コードを他のコードと同じ基準で扱うこと、つまり正確性・セキュリティ・保守性であり、エンジニアが「正しそうでチェックを通る」という理由で、もはや完全に理解していない出力を受け入れるという微妙な失敗を監視することです。

勤勉さが生み出す具体的成果物は検証チェックリストです：AI生成出力が本番に届く前に通過すべき明示的なチェックセットです。この検証チェックリストは、チームが固有のニーズに基づいて内部で作成するものです。チェックリストには検証の4つの次元すべてに対処する質問を含めるべきです：正確性、セキュリティ、保守性、人間の理解。

チェックを自動化できる場所では自動化すべきです。回帰テストスイートとevalセットは、正確性と動作検証をレビュアーの判断から、すべての変更で実行されるゲートに変えます。チェックリストは「真であるべきこと」を定義します。Evalsとテストは、チームが毎回手作業で導き出すのではなく反復可能であることを証明する方法です。そのチェックリストを持つチームは良い意図を反復可能なゲートに変えましたが、持たないチームはデフォルトでAI出力を信頼し、レビュアが重要な点を捕捉することを期待しています。

#### **要注意：**
説明できないマージ

チームがAIアシストコーディングを採用し、著しく速く出荷するようになりました。3週間後、生成された変更がコードレビューとテストを通過し本番にリリースされましたが、そこからデータが漏洩しました — その入力を検証しなかったからです。インシデントレビューで、作者はなぜコードがその入力をそのように扱ったか説明できませんでした：見た目はもっともらしく、テストはグリーン（成功）で、チェックリストが強制したであろう質問は誰も聞きませんでした：これをマージする人は、これが何をするか、なぜそうなるか説明できますか？ 速度が知識を静かに置き換えていました — これこそが勤勉さが捕捉すべき判断力の低下です。

#### **コスト・複雑さ・リスク**

| **コスト** | AIアシスタンスはコード生成コストを下げ、レビューに届く量を増やします；検証チェックリストがその量が品質バーを圧倒しないように保ちます |
| **複雑さ** | 難しいのは文化的側面で、技術的ではありません：AI生成コードを手書きコードと同じレビュー基準で扱うこと、特に速く出荷され、正しく見えるときは |
| **リスク** | 最大の失敗モードは判断力の低下：浅いチェックを通過したため、もはや内容を理解していない出力を出荷し続けるチーム。誰も検証しなかった入力が本番に届くまで進行する |

## Screen 6 (S06) — 運用サポート

### 運用サポート
デバッグと運用上の問題解決のサポート

本番デプロイメントがチームを驚かせる時がいつか来ます。その時、アーキテクトは「チームが見ているもの」と「なぜそれが起きているか」を結びつける人物です。アーキテクトはチームのスキル向上にも責任を持ち、次回は自分たちで問題解決できるよう権限を与えます。この画面は、サポート役割、それを定義する「症状から原因への推論」、チームの自律性構築についてです。

### サポート役割は翻訳であり、消火活動ではない

運用上の問題が発生すると、チームは通常、原因ではなく症状を特定します。例えば、レイテンシが急増し、出力が劣化し、ツールが失敗し始めたと気づきます。チームはアーキテクトを呼びます。アーキテクトの価値は、運用症状をアーキテクチャ原因に結びつけることです：Module 2で本番システムのために構築した診断規律と同じものを、デプロイメントを所有するチームのサポートに適用します。1つのインシデントを自分で解決するのは消火活動；チームに「症状→原因」パスを教え、将来再び使えるようにするのは持続するサポートです。

### 症状をアーキテクチャ原因に結びつける

raw の "connect symptoms to architecture causes" に対応。運用上の症状（レイテンシ急増、品質劣化など）からアーキテクチャ上の根本原因（モデル変更、検索ドリフト、キャッシュ問題など）を推論するプロセス。

多くの運用症状は少数のアーキテクチャ原因に帰着します。これらを特定することで、チームは見ているものからどこを見るべきかを明確に推論できます。

#### 症状 → 可能性が高いアーキテクチャ原因 → 初動対応

| 症状 | 可能性が高いアーキテクチャ原因 | 初動対応 |
|---|---|---|
| 出力品質が徐々に劣化したが、コード変更はない | モデルまたはプロンプト変更、またはコーパス成長に伴う検索ドリフト | evalセットと比較；モデル・プロンプト・コーパスで何が変わったか確認 |
| レイテンシ急増 | コンテキストサイズ増大、ツール遅延、またはキャッシュミス | テレメトリとリクエストトレースで最遅スパン特定；リクエスト当たりトークン数と最遅ツール呼び出しをチェックし、キャッシュ動作を確認 |
| 断続的ツール失敗 | 認可、レート制限、または処理されないエラーパス | 失敗ツールの認証と制限を検査；失敗呼び出しを1つエンドツーエンドでトレース |
| コスト上昇（使用量変更なし） | モデルティアが徐々に上昇、またはキャッシング劣化 | 予算モデルに対してリクエスト当たりモデルティアとキャッシュヒット率をチェック |

### 自律性を構築する：ランブック（Runbook）とエスカレーションパス（Escalation Path）

自律性は機能するチームに組み込まれます。ランブックは既知の「症状→原因→アクション」パスをキャプチャし、チームがアーキテクトなしで再発問題を解決できるようにします。上の表は良いランブックの基礎です。エスカレーションパスは誰が何を扱うか、問題がいつチームを離れるかを特定するので、人々は自分で解決できるものとエスカレートすべきものの境界を知っています。チームには常にデプロイメント用ランブックを保持し、明確なエスカレーションパスを定義するよう奨めてください。目標は、新しい問題が発生したときのみあなたを必要とするチームです。既に教えた問題のためにあなたを必要とするチームではありません。

#### **要注意：**
四半期レビューまで待ったドリフト

サポートチームは、1四半期、デプロイメントのダッシュボードがグリーンのまま、回答品質が静かに低下しているのを見ていました。誰も緩やかな低下とその原因を結びつけませんでした：インデックスが追いつかなかった成長する検索コーパスです。症状は全体で見えていましたが、「コード変更なしの緩やかな品質低下」が「モデル、プロンプト、または検索ドリフト」を指すというランブックエントリが欠けていました。そのパスが書かれていれば、一次対応エンジニアが午後中に問題を解決できました；しかし、なければレビューまで待つことになります。

#### **コスト・複雑さ・リスク**

| **コスト** | 症状→原因パスを教えるのは、インシデントを直接修正するよりアーキテクトの時間をより前段階で要しますが、繰り返すのではなく将来の負荷を軽減する唯一のサポート形式です |
| **複雑さ** | 難しいのは消火活動への衝動に抵抗すること：迅速な修正は自分で解決することですが、持続可能な修正はチームにランブックエントリ作成を支援し、エスカレーションパスを特定させることで、次の問題をチームがあなたの助けなしで解決できるようにすることです |
| **リスク** | 最大の失敗モードは誰も原因に結びつけない緩やかな劣化で、スケジュールされたレビューが捕捉するまで走り続け、チームが開始当日に捕捉することがありません |
