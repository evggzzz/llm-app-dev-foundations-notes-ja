**問題文**

- A. Anthropic Client SDK で Messages API を呼び、ファイル編集をテキストで指示し、ツール実行コードは書かない。
- B. Claude Agent SDK を組み込み、必要なファイルツールを有効化し、SDK のメッセージをストリーミングし、ツール使用周りに hooks を追加する。 ← 正解
- C. `allowedTools` をファイルツールに設定し `bypassPermissions` を使い、最終結果だけをストリームし、他のツールは利用不可とする。
- D. Claude Managed Agents をクラウドサンドボックスで動かし、各チェックアウトをそこへコピーし、セッションイベントを戻す。

**解説**: Claude Agent SDK は Claude Code の自律的エージェントループをアプリに組み込む。プロンプトを評価し、ツールを要求し、結果を受け取り、最終結果が出るまで繰り返す。ツール実行ループを SDK が引き受けるので、開発者がゼロから書く必要はない。ローカルデスクトップユーティリティでは、ファイル操作・検索・実行・オーケストレーションの組み込みツールをそのまま使え、ストリーミングメッセージで UI を駆動し、hooks で確定的なチェックを挟める。

- D. ケーシングに依存しない安定したステータスコードを `output_config.format` で公開し、stop reason を確認した上で、パースしたコードをキューへマップする。 ← 正解

**解説**: Structured Outputs は、downstream のソフトウェアがスキーマに従うパース可能な JSON を必要とするときの正しい基盤。`output_config.format` で JSON Schema を Claude の最終応答に指定し、レスポンスコンテンツの検証済み JSON テキストを読み出してアプリコードでパースする。

ただしスキーマ制約があっても出力扱いには防御設計が要る。Anthropic は `stop_reason: "refusal"` と `stop_reason: "max_tokens"` が通常のスキーマ適合ビジネスデータとして扱うべきでない応答を生みうると文書化している。さらに string enum や const の大文字・小文字の区別は保証されない。ルーティングでは、違いがケーシングだけのラベルを避け、意味的に異なる安定コードを使い、検証後にレガシーのキュー名へマップする。

A（自分の誤答）のプロンプト依頼は JSON の一貫性を改善しうるが、スキーマ適合を保証する文書化された機構ではない。構文エラーのリトライだけではケーシングのみの違いや refusal、不完全出力という意味論的リスクを取りこぼす。B は Structured Outputs を使いつつ enum のケーシング非保証という文書化された制約と衝突する。C は prefilling が JSON 出力と両立せず、Opus 4.8 ではサポートされない。加えて stop reason 確認前にルーティングするのは unsafe。

**参照**: Prep M2 S2「Prompting Craft — Teaching」（Structured Outputs: `output_config.format`、`stop_reason` の確認、prefilling との非両立）
